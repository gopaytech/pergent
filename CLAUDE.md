# pergent

CLI tool that runs agentic PR/MR reviews in CI/CD pipelines by spawning `opencode` as a subprocess.

## Architecture

- `cmd/main.go` — CLI entrypoint, flag parsing, orchestration
- `cmd/agent.go` — `pergent agent`: flags, checkout checks, scrub, run, delivery, exit codes
- `internal/skill/` — Parses `.md` skill files (YAML frontmatter `name`/`paths`/`exclude`/`cross_batch` + body); `Prompt()` adds the default `## Blocking` section and pergent's fixed output-format instructions. `LoadDir` takes `*.md` files and `<name>/SKILL.md` folders, symlinks followed (ConfigMap volumes); a folder without `SKILL.md` is an error
- `scope/` — Public package (`github.com/gopaytech/pergent/scope`, imports no pergent `internal/` package): the glob matcher (`Match`, `MatchAny`, and `CheckPattern`, which `internal/skill` runs on `paths`/`exclude` at load because `Match` reports a bad pattern as no match), the path-based default exclusions (`Attributes.PathRule`: lockfile, vendored, generated by `.gitattributes`, where the last matching line wins and `-linguist-generated`, `linguist-generated=false` or `!linguist-generated` un-marks), the generated-file header test, and `Decide`, which applies one skill's `paths`/`exclude` to a file. pergent.sh imports it, so the rule strings are a contract
- `graph/` — Public package (`github.com/gopaytech/pergent/graph`, imports no pergent `internal/` package): the `pergent-graph/v1` format, strict `Decode`/`ReadFile`/`Validate`/`Encode` (unknown fields refused, errors name the field and index, never the value), `EdgeAllowed`, `ValidName`, `ValidPath`, `MaxBytes` 64 MiB. pergent.sh can use it to check an upload
- `internal/diff/` — Splits a unified diff into per-file patches, classifies default exclusions (deleted, binary, no content changes, then `scope`'s path rules and the patch's generated header), and groups files into token-budgeted batches. `Classifier.ReviewDeleted` (set by `review.Run` from `--check-deleted`) lets a deleted file through to batching unless it can't be batched (binary, no hunk, `NotReviewed`, or denied by `Classifier.DeniedDeleted`, which `review.Run` sets to `config.ReadDenied` with the runs' deny flag: still `deleted`); `FileDiff.Copied` marks `copy from`
- `internal/finding/` — The `Finding` type (file, line, end_line, severity, title, explanation, fix, suggestion), stable fingerprints, dedup
- `internal/review/` — Runs a whole review: per skill selects files, batches them, runs one opencode run per batch (plus a repair run, an optional cross-batch run and a verification run), and decides each skill's verdict; one shared concurrency limit and time budget
- `internal/config/` — Resolves config (flags > env > auto-detect), generates temporary `opencode.json`
- `internal/runner/` — Spawns `opencode run` subprocess (records per-step usage and tool targets), parses NDJSON output, classifies the run (completed or failed with a cause), classifies provider errors (`provider.go`: `quota`, `billing`, `auth`, `rate_limit`, from the error event's status, type and response body), retries transient provider errors, builds opencode's environment from an allow-list for a generated config (`PERGENT_OPENCODE_ENV` adds names, parsed by `config.ExtraEnvNames`), enforces timeout and step limit (a stopped run kills opencode's whole process group, so its children die too; Unix only); passes opencode's stderr through redacted line by line; starts every run with `--standalone`, a state directory of its own and `PWD` set to the repo path (opencode 2 takes its project directory from `$PWD`, not the working directory); `version.go` refuses an opencode older than 2.3.2
- `render/` — Public package (`github.com/gopaytech/pergent/render`, imports no pergent `internal/` package, redacts nothing): builds the review comment from `render.Skill` values. One header (headline with verdict and confidence, meta line, reason only when the score is below 5 or capped, skills table for several skills, failures), then the `**Summary:**` line (one skill, one batch, one summary), one findings list across skills (blocking open, suggestions collapsed), the Dismissed list, the details (a `- **Batch N of M:**` list for one skill with several batches; with several skills a `#### <skill>` section each holding its summary and checks; the checks by area, a heading and a `Check`/`Status`/`Detail` table per `Check.Section`, failed first, no-area checks last, under an `Other checks` heading beside named areas and with none alone, merged across batches per skill) and one `Files (N)` list (a reviewed deleted file is marked `(deleted)` and a rename `(renamed from <old>)`, by `Skill.Deleted` and `Skill.Renamed` (`render.Rename{Path, From}`), both omitted from JSON when empty so older golden inputs are unchanged), then the notes, the footer and the hidden findings block. A finding whose file is in any skill's `Deleted` shows as `path (deleted), line N` (or `lines N–M`) in a `<code>` span, never a link even with `FileURL`, and its row has no suggested change. Includes the shrink steps for a size limit (`shrinkSteps`, summaries cut last). `Options.Layout` (`blocks.go`: `Block`, `DefaultLayout`, `ParseLayout`; blocks `summary`, `findings`, `dismissed`, `checks`, `files`, each open or collapsed or left out; nil or invalid means the default; `findings` is required; it never changes a verdict, count or the fixed header and footer, and `Short` wins over it). Options: `Commit`, `FileURL` (`GitHubFileURL`/`GitLabFileURL` build one), `DismissCommand`, `Version`, `FindingsTitle`, `FindingNote`, `Inline` (fingerprints posted inline, left out of the lists), `Footer` (caller text before the hidden block), `MetaNote` (last part of the meta line), `HeaderNote` (one caller line in italics after the header, made inert by `wrappedText`, kept by `Short`, a layout and every shrink step), `Short` (leaves out the Files list and the passed and n/a checks, with no note; the size-limit steps still apply). Also `SkillScore`/`ReviewScore` (the confidence caps), `AssignIDs` (finding IDs) and `ApplyDismissals` (moves dismissed findings into a Dismissed section and recomputes verdicts). Model text goes through `lineText` (one line), `wrappedText` (between pergent's own `**`/`_`), `cellText` (table cell) or `blockText` (several lines) in `prose.go`. `lineText` leaves a line-start `#`, `>` or `-` alone, so a summary, an area name or a skill name is written only after a prefix of pergent's (`**Summary:** `, `- **Batch N of M:** `, `#### `). Fenced code is written again inside a fence pergent builds (no info string), a container of pergent's. A code span is the model's own bytes, kept only on a narrow rule (it starts at the line's start or after a space or tab, ends at the line's end or before a space, tab or `).,:;!?`, a line with a `$`, an odd number of backticks or any backtick outside a span keeps no span, and in `wrappedText` the line's start and end don't count; otherwise a URL or math could take a backtick); a cell keeps none. Every other `@`, `<`, `[`, `]`, `|`, stray backtick and entity start is broken with a zero-width joiner or a backslash, and `|` in a cell is `&#124;`. `testdata/golden` pins the comment byte for byte
- `internal/output/` — Converts per-skill review results to `render` types (redacting every text field first) and calls `render`; parses the hidden findings block back for `--previous-review`
- `internal/result/` — Agent-mode result (per-skill `runs`, `EncodeUsage`): schema v1 types, error codes, finding IDs (`render.AssignIDs`), 10 MB size cap (`Encode`), delivery to file/stdout/HTTP (`Deliver`). `Files.Deleted` (`deleted`) and `Files.Renamed` (`renamed`, `Renamed{Path, From}`) are `omitempty` and additive (`schema_version` stays 1); `files.reviewed` holds a deleted file only when `files.deleted` lists it; `Build` clears `suggestion` on a finding on a deleted file, `redactSkill` redacts both fields
- `internal/checkout/` — Scans a checkout for instruction files and symlinks (to the root, outside it, or to a file a caller's rule denies), and lists the regular files a caller's rule denies (`DeniedFiles`, a name judged as written and in lower case); CI mode (`cmd/scrub.go`) and agent mode (`handleInstructionFiles`, `deleteDeniedFiles`) decide what to delete or refuse
- `internal/redact/` — Removes credentials (token env values, bearer tokens, URL keys) from the comment and logs
- `internal/platform/` — GitHub/GitLab API clients for fetching diffs and posting/updating comments
- `internal/graphify/` — Converts graphify 0.9.112 `graph.json` (default output: networkx `links`, `graph.schema_version` 1 and `graph.graphify_version` `0.9.112`; `--no-cluster` output is refused) to v1. The security gate: decodes only `id`, `label`, `file_type`, `source_file`, `source_location` and link ends, relation and confidence; keeps `code` nodes (file: line 1 and the base name or a path-suffix label; method `.Name()`; function `Name()`; type: an identifier a `contains` from a file, a `method` edge or an inherits edge marks), symbols only in code-extension files, drops nodes in files `config.ReadDenied(_, true)` denies (as written and lower case); keeps `EXTRACTED` and `INFERRED` links, drops `AMBIGUOUS`; own ids `n1...` in (file, line, kind, name) order. Commit: `--commit`, else graphify's `built_at_commit` (the HEAD of the git repo that holds the output folder, missing outside one)
- `internal/graphpack/` — `OldLines` (old-side lines of a patch), the symbol lookup (innermost with `end_line`, else the last symbol at or above; a function or method beats a type) and the `graph-context.md` hint: callers, then importers, then callees, 10 callers and 10 callees per symbol, `MaxTokens` 2000 by exact bytes with room for the cut line; never says "no callers"

## Key Concepts

- **One opencode run per batch.** Each `--skill` is reviewed over the changed files in its scope (`paths`/`exclude` plus default exclusions). `internal/diff` groups those files into batches that fit a quarter of the model's context, and `internal/review` runs one `opencode run` per batch, all skills and batches in parallel. Results are combined into one comment.
- **Structured findings.** The prompt (`skill.Prompt()`) tells the model to end with one `json` block of findings; severity is `blocking` or `suggestion`. The answer also carries `confidence` 1–5 with `confidence_reason`, and a finding may carry `end_line` and `suggestion` (exact replacement text, at most 10 lines); bad values are dropped, never a repair run. The answer is the last block with a `findings` key; a bad or unreadable last block is malformed, never replaced by an earlier block (that may be an example of the shape). A malformed answer gets one repair run, then the batch is a failure. Skills must not carry their own output-format instructions.
- **Change description.** `review.Request.Description` is the change's title and description (CI mode: `Platform.FetchChangeDescription`, a failure is a warning; agent mode: `--change-description`, default `$PERGENT_CHANGE_DESCRIPTION`, same trust and warn-and-ignore rules as `--previous`). `changeText` removes HTML comments (one left open hides the rest), trims it and cuts it to 16 KiB. `reviewBatch` and `crossBatch` attach it as `change-description.md` with `changeMessage`; verification and repair runs never get it, so the author's text can't talk a blocking finding away. `changeMessage` is the design: intent can excuse a change in behaviour but never a blocking problem, a contradiction is always a `suggestion` (verification couldn't confirm a blocking one), a promise the run doesn't see is not reported (a run sees part of the change), and the description itself is never a finding. The file is data; the wording is all that stops it swaying the review run.
- **CI results.** Agent mode only: `--ci-results` (default `$PERGENT_CI_RESULTS`, same trust and warn-and-ignore rules as `--change-description`) is a file of the CI job results of the change. `review.Request.CIResults` is cleaned by `ciText` in `Run` (invalid UTF-8 replaced, ANSI escapes and control bytes other than tab and newlines removed (a NUL makes opencode's read fail the run), `redact.String`, trimmed, cut to 64 KiB (`maxCIResults`) at a rune start with a note); blank means none. `reviewBatch` and `crossBatch` attach it as `ci-results.md` with `ciMessage`; verification, repair and impact runs never get it. `ciMessage` says it is data, to be used to see where to look and what CI already caught, that a CI result is never a finding and that a passed job never excuses a problem in the code. It takes room from the batch: `reviewSkill` packs with the batch budget less `diff.EstimateTokens(CIResults)`, floored at half; a file over that but within the full budget gets a batch of its own, and only a file over the full budget is oversize (`carveOut` only rewrites sentences and counts nothing). Without it, prompts and attachments are unchanged.
- **On-demand diffs.** `review.Run` (only with a generated config, i.e. `OPENCODE_PROVIDER` set) writes each eligible file's patch (some skill reviews it, no default exclusion, patch fits a batch, neither its path nor a rename's old path denied by `config.ReadDenied`) to `NNNN.patch` plus one `index.txt` (diff file, size, `strconv.Quote`d path) in one `pergent-diffs-*` temp directory, removed when the review ends or a run's own goroutine panics. Nothing is attached and `changed-files.md` is unchanged; batch, cross-batch and verification runs get one message sentence naming the index, unless their own diff covers every indexed file. A directory or file that cannot be written is a warning, never a failure. Findings are not filtered by file; the scope is prompt wording only. A run can read the diffs; nothing proves it does.
- **Deleted files.** Off by default: `--check-deleted` (bool, default false; `PERGENT_CHECK_DELETED`, flags > env, a bad value is a config error; `Request.CheckDeleted`, which `review.Run` copies onto its own `Classifier.ReviewDeleted`, so the request decides whatever classifier the caller passes). Off changes nothing, byte for byte: every deleted file is skipped as `deleted`. On: a deleted file in a skill's scope is batched like a changed file (its removed lines; `deletedBatchMessage` names the batch's deleted files, says `line` is the line in the deleted file and asks for no `suggestion`) and judged on whether removing it is safe, and the batch also searches for what still uses it. A deleted file `config.ReadDenied` denies (deny flag = `Sandbox.Hardened`, as in `eligibleDiffs`) keeps rule `deleted` (`Classifier.DeniedDeleted`): its removed lines never reach a run, and it goes on the list by path only. A rename with content changes (`renamedAway`: old path not at head, not `Copied`, switch on) is named by its batch as `"old" renamed to "new"` in `renamedBatchMessage` and gets the same reference check; it is still reviewed under its new path and is not in `Renamed`. A deleted path that also has a non-deleted entry (a type change, `reviewer.live`; `gone` is false for it) is never in `Deleted`, never on the list, reviewed once, and the diffs index keeps its non-deleted patch. One reference list per skill, `deleted-files.md` (`strconv.Quote`d, 200 entries then `... and N more`), holds `reviewer.referenceList`: the deletions that were not batched, and the pure renames (`pureRename`: `OldPath` set, not deleted, not `Copied`, rule `no content changes`; old or new path in scope by `renameInScope`, which also applies the path rules; old path not a `Path` of another file, i.e. not re-created), as `"old" renamed to "new"`. Batch 1 carries it with `deletedMessage`, the verification run gets it with every deletion in scope (`verifyDeletedMessage`), cross-batch and repair never; `carveOut` makes room in the diff sentences. A skill with a list but no batch gets one `reviewBatch` call on zero files (no `diff.patch`, `noDiffMessage`, label `references`), folded in by `takeDeletedOnly`. A deletion that can't be batched (binary, no hunk, `NotReviewed`) keeps rule `deleted` (`Classifier.Exclusion`, never `binary` or `no content changes`, which don't block approval); a deletion that a skill's `paths` or `exclude` skip keeps `deleted` for that skill, not `out of scope` (`Select`); vendored, lockfile and generated deletions keep their own rule, the generated header read from the removed lines (`scanPatch` with `readRemoved`), unless the skill's `paths` opt in. Counting: a deleted file is in `Reviewed` and `SkillResult.Deleted` only when its batch finished; a rename is moved out of `Skipped` into `Reviewed` and `SkillResult.Renamed` (`review.Rename{Path, From}`) only when a finished run saw the list (batch 1, or the no-diff run), by `countRenames`. Renames past the cap, or on a list no finished run saw, stay `no content changes` with the note `N renamed files were not checked for references`; deletions past the cap keep `deleted`. A failed or unstarted batch with deleted files, or run with the list, fails the skill (a no-diff failure names no file). `deletedPatch` gives the verification of a blocking finding on a reviewed deleted file that file's patch as `deleted.patch` (`deletedPatchNote` if it can't be written). A list that can't be written is the note `deletedNote`, not a lost run. A deleted file's `suggestion` is cleared in the comment rows and the result (not in the hidden findings block).
- **Code graph.** Off by default: `--graph <file>` (local, CI and agent mode; no env variable; a trusted input in agent mode, so inside `--repo-path` is a usage error) reads a `pergent-graph/v1` file of the default branch in `cmd/graph.go` `readGraph`; a missing, unreadable, invalid or too-big file logs one `graph: skipped: <reason>` line and the review runs as with no flag (no note, byte for byte the same). `pergent graph convert --provider graphify --in <graphify-out> --out <file> [--commit <sha>]` (`graphMain`, exit 0/1/2, reads no LLM key or token) writes it with mode 0600 through a `.tmp` rename. `review.Request.Graph` becomes one `graphpack.Index` per review; `reviewBatch` (only a batch with a diff: never repair, cross-batch, verification, `references` or impact runs) attaches `graph-context.md` last among its files and adds `graphMessage` last in the message; an empty pack attaches nothing. The pack filters entries with `config.ReadDenied(_, Sandbox.Hardened)` as written and in lower case; a rename (not a copy) is looked up under `OldPath`. A write failure (`writeGraphPack`) warns `graph: skipped for <skill> <label>: <err>` and adds the one note `graphNote`; it never fails a batch or moves a verdict. Batching and the batch budget do not change, and there is no new result field (the usage data already lists the attachment and its bytes).
- **Usage per run.** Every opencode run records its prompt size, attachments, tokens, tool totals and each step's tokens and tool calls (`review.RunUsage`, `result.Run`). A tool call carries a tool name from a fixed set and a target class (`repository`, `pergent`, `tool_output`, `outside`), never a path, and no model text is kept. The comment never reads it. There are two ways out: `skills[].runs` in the agent result and `--usage-file` (local and CI mode, off by default, no env variable, mode 0600; a write error is a warning). Raw counts only, no prices.
- **Verdicts.** Each skill is `no_blocking_issues`, `has_blocking_issues` or `failed` (any batch failure). Blocking findings are re-checked by a separate verification run before they count; `cross_batch: true` adds one run for problems spanning batches.
- **One budget, one concurrency limit.** `--timeout` bounds the whole review (not each run) and `--concurrency` caps opencode runs in flight across all skills and batches.
- **Previous review.** `--previous-review` reads the hidden `<!-- pergent:findings ... -->` block (last line of the comment) and attaches each skill's findings, only when non-empty. Comments from older versions have no block and count as a first review; a corrupt block logs a warning and is ignored. A fingerprint the model reuses is kept only on the same file and line as the previous finding: a dismissal is keyed by fingerprint, so a new finding elsewhere must not inherit one.
- **Read-only agent.** The generated `opencode.json` defines a `pergent` agent (set as `default_agent` and passed via `--agent`) whose sandbox is an allow-list: `"*": "deny"`, then `read` (the file rules, `*.env` and the like denied), `glob`, `grep`, `external_directory` and `doom_loop`, so a tool opencode adds later is denied without a change. Rules are last-match-wins and `encoding/json` sorts `*` first. The block is written at top level and again on `agent.pergent.permission`; the agent copy is load-bearing, because opencode 2 appends an agent's rules after every global one and without it a global `agent.pergent.permission` allow-all handed the model `shell` and `edit` (pinned by an e2e test). The `external_directory` allows exist because `"*": "deny"` would otherwise deny pergent's own temp files and the tool-output folder. `doom_loop` is not an opencode 2 permission action and is kept for compatibility. The config also sets `"snapshot": false`, the 1.x key, which 2.3.2 honours (no snapshot store, nothing written to the checkout's `.git`; an e2e test pins it). `grep` and `glob` still don't apply the read rules (and `grep` searches hidden files), so a denied file is deleted from the checkout before any run (`checkout.DeniedFiles`: regular files, a name judged as written and in lower case, only the root's `.git` skipped): platform CI mode in `scrubCheckout` (a failure is a warning), agent mode in `deleteDeniedFiles` (always, with its wider rules; a failure is `internal`). `--local` deletes nothing. `OPENCODE_DISABLE_PROJECT_CONFIG=true` and `OPENCODE_CONFIG_PROJECT_DISABLE=true` stop the reviewed repo's own opencode config from overriding this (2.3.2 reads the new name first, so a caller's `false` there would win; the runner drops inherited copies and sets both; pinned by an e2e test), the allow-list doesn't carry an inherited `OPENCODE_CONFIG_CONTENT` (merged over the config file, it loosened the sandbox) or `OPENCODE_CLI_CONFIG_CONTENT`, and `OPENCODE_DISABLE_CLAUDE_CODE=true` (generated config only) stops opencode 2 reading `CLAUDE.md` files. For the same reason it doesn't carry `OPENCODE_CONFIG_DIR` (it is loaded as a config directory with plugins, so one inside the checkout would run the change's code), `OPENCODE_FLAGS` (unvetted experimental features), `OPENCODE_DB` (parallel runs would share one SQLite file and the user's credentials), `OPENCODE_TEST_HOME` and `OPENCODE_SIMULATE` (test hooks), and the runner sets `OPENCODE_DISABLE_AUTOUPDATE=true` (no update check or mid-review upgrade); all generated config only, own-config runs pass them through. opencode 2 never starts language servers, but `lsp: false` is kept.
- **Own-config mode.** With `OPENCODE_PROVIDER` empty pergent writes no config: no sandbox, project config on, default agent, and `GITHUB_TOKEN`/`GITLAB_TOKEN` stay in opencode's env (it may sign in with one; the runner removes them only with a generated config). `config.Resolve` therefore refuses it in platform mode (an unset CI variable expands to ""), unless `PERGENT_USE_OPENCODE_CONFIG=true` (a bad value is a config error); then it warns. `OPENCODE_MODEL` without a provider is part of that error, a warning with `--local`. `--local` needs no opt-in; agent mode always requires a provider. Every mode needs opencode 2.3.2 or later (see Version check). The prompt lives only in the config, so `runWithPrompt` (the one place every prompt passes: batch, repair, cross-batch, verification) attaches it as `review-instructions.md`, first among the run's files, adds `promptMessage` to the message, and removes it with the run.
- **Config isolation.** `opencode.json` is written to a temp directory and passed via `OPENCODE_CONFIG` env var. The agent prompt is not in it: opencode expands `{env:}`/`{file:}` over the whole config text, so a skill body naming `{env:GITLAB_TOKEN}` would leak it and a stray `{file:x}` would fail every run. The prompt goes to `agent-prompt.md` (0600) beside it and the config holds `{file:<abs path>}`; a file's content is not scanned again. Each run (and each retry) also gets its own temp `XDG_DATA_HOME` (with the user's `auth.json` copied in, which opencode 2 imports into the new database, so a 1.x login still works): parallel runs sharing a fresh data dir race on opencode's SQLite migration and the losers exit 1. A login made with opencode 2 lives only in the user's `opencode.db` (`credential` table) and does not reach a run; `opencode auth export` prints a list the import does not read, and pergent copies no database. Keys come from `OPENCODE_API_KEY` (generated config) or the provider's env or config (own config). It gets its own empty `XDG_STATE_HOME` too (`config.StateDirPrefix`), and every `opencode run` gets `--standalone`: a plain run attaches to a shared server registered by `opencode service start`, which ignores `OPENCODE_CONFIG`. The data directory's name (`config.DataDirPrefix`) must not start with `pergent-`, or the `pergent-*` read allow would cover `auth.json`; only its `opencode/tool-output` folder is allowed, since opencode points the model at long tool results there. With a generated config opencode's environment is an allow-list, not pergent's environment minus a strip list (`allowedEnv` in `internal/runner/runner.go`): `PATH`, `HOME`, `USER`, `USERNAME`, `LOGNAME`, `SHELL`, `TMPDIR`, `TMP`, `TEMP`, `LANG`, `TZ`, `TERM`, the proxy variables (both cases), `SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS`, `NODE_USE_SYSTEM_CA`, `NODE_USE_ENV_PROXY`, `NODE_TLS_REJECT_UNAUTHORIZED`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `OPENCODE_API_KEY`, and the prefixes `LC_`, `AWS_`, `GOOGLE_`, `VERTEX_`, `AZURE_`, `CLOUDFLARE_`, in every generated-config mode. Everything else is dropped (so are `GITHUB_TOKEN`, `GITLAB_TOKEN`, every other inherited `OPENCODE_*` and `OTEL_*`; the reasons per `OPENCODE_*` name are in the comment in `BuildCommand`). `PERGENT_OPENCODE_ENV` (env only) adds exact names, comma-separated; `config.ExtraEnvNames` parses it and refuses a name that is not `[A-Za-z_][A-Za-z0-9_]*`, starts with `OPENCODE_` or `PERGENT_`, or is `GITHUB_TOKEN`, `GITLAB_TOKEN`, `PWD`, `XDG_DATA_HOME` or `XDG_STATE_HOME`, so the hatch can't reopen what pergent strips or sets. `config.Resolve` (CI, `--local`, when a provider is set) returns that as a config error and `parseAgent` as `usage`. pergent then appends `OPENCODE_CONFIG`, both project-config switches, `OPENCODE_DISABLE_CLAUDE_CODE`, `OPENCODE_DISABLE_AUTOUPDATE` and `PWD`; `runAttempt` sets `XDG_DATA_HOME` and `XDG_STATE_HOME`. Own-config runs keep the full environment.
- **Run outcome.** Every opencode run is `StatusCompleted` (the model's own final answer) or `StatusFailed` with a `Cause` (context overflow, timeout, opencode error event, step limit, non-zero exit, no answer, or cancelled when the caller's context ended, e.g. SIGTERM). A line over 16 MB stops the parse (`Transcript.ReadErr`): the run is `no_answer` with its own message, never a pass on an earlier answer. Only assistant text from a step that ended on its own counts as the answer; `synthetic` text and text outside `step_start`/`step_finish` never do. A failed batch makes its skill's verdict `failed` and is reported in the comment and log, but keeps the CI job green; only config errors before any review exit non-zero.
- **No auto-compaction.** The generated config sets `compaction.auto: false` and leaves model limits to opencode's registry (`--context-limit` overrides; `--max-tokens` is deprecated and ignored). The model is always declared under `provider.<id>.models`, or opencode can't find models behind a custom base URL.
- **Retries.** An error event is opencode 2's `{type, message, status, response.body}` (the 1.x `{name, data}` shape is not read; `EventError.Name` is the `type`, `ResponseBody` is used only to classify and never printed). A run that fails on a transient error (`Transient`: 429, 5xx, `provider.rate-limit`/`transport`/`internal`/`timeout`, or, for a non-provider type with no status, `transientPattern`) is started again with backoff, within the review budget: once for a provider error (`provider.*`, `maxProviderRetries`; opencode already retried it itself, so a persistent 500 holds a run about 86s per start), up to 3 times otherwise, **except** quota, billing and auth errors (`Classify` in `provider.go`, one strict rule table: an unknown 429 is `rate_limit`, a 5xx is no class; `provider.auth` or a 401/403 is `auth`, and a stream `insufficient_quota` with no status is `quota`). Those stop opencode on their error event (`progressWriter.onError`) and are never started again: pergent.sh moves the review to another model. The class reaches the agent result as `provider_error` (per failure and once at the top, the most severe; `provider` and `model` come from `OPENCODE_PROVIDER`/`OPENCODE_MODEL`, since opencode 2's error names no provider); the response body is read for the class only and never reaches a cause, log line, comment or result. A context overflow is detected from opencode's own phrases (`runner/overflow.go`, copied from opencode v2.3.2 `provider-error.ts`) in the message and body text, with status 0 or 4xx and never 429; there is no type check. An error event pergent cannot read fails the run.
- **Version check.** `runner.CheckOpencodeVersion` runs `opencode --version`. opencode 2.3.2 or later (`MinOpencodeVersion`) is required: an older or unreadable version is refused, as a config error in CI mode and `--local` (and `pergent test`), as `internal` in agent mode (checked after `prepareAgent`). It reads the version from `opencode X.Y.Z` (or `vX.Y.Z`) when a line names opencode, else from the first `X.Y.Z`, so a notice or an address printed first is not taken for it. A pre-release of the floor (`2.3.2-beta.1`) is refused. A newer one than `TestedOpencodeVersion` gets a warning. `cmd` calls it through the `checkOpencodeVersion` variable so tests that don't test the check can replace it.
- **Agent mode.** `pergent agent` reviews `--base..--head` in a checkout the caller prepared and delivers a versioned JSON result (`docs/agent-result-schema.md`). It holds no platform token and never calls GitHub/GitLab; CI mode is untouched. Details:
  - Trusted inputs only: instructions, skills, `--previous`, `--carried`, `--dismissals`, `--change-description` and `--ci-results` come from paths passed in (the description's and the CI text are still the author's); one that resolves inside `--repo-path` is a usage error, as are a `--result` file, `$HOME` or `$XDG_CONFIG_HOME` there, and duplicate skill names. The checkout's `AGENTS.md`/`CLAUDE.md`/`CONTEXT.md` are never loaded.
  - `--scrub-instructions` deletes those files (root included), symlinks resolving outside the checkout and symlinks whose real target `config.ReadDenied(rel, true)` denies (`safe.txt -> prod.env`); without it, nested files or such symlinks give `untrusted_instructions`. A directory the scan cannot read is `internal`. opencode loads nested instruction files on every read whatever the project-config switch says.
  - `--carried` is a JSON file `{"<skill>": ["path", ...]}` of files a previous review covers: `reviewSkill` leaves them out of the batches (still in `changed-files.md`), drops previous findings on them, and reports them as `files.carried`. Same trust and warn-and-ignore rules as `--previous`.
  - `--dismissals` (default `$PERGENT_DISMISSALS`) is a JSON file `{"<skill>": [{file, title, severity, reason}, ...]}` of findings people rejected: `reviewBatch` and `crossBatch` attach a skill's list as `rejected-findings.json` with `rejectedMessage`, `verify` gets only the `blocking` entries with `rejectedVerifyMessage`, the repair run none. Data, never instructions; same warn-and-ignore rules as `--previous`. Logged as `dismissals: <skill>=<n>`, not part of the result.
  - `--linked-repos` (default `$PERGENT_LINKED_REPOS`; a flag with an env default, as `--change-description`) is a JSON file `[{name, path, watched, can_block, error}]` (`review.LinkedRepo`, `cmd/linked.go`), at most 3. A file that can't be used (unreadable, malformed, more than 3, a duplicate or empty name: `failedLinks` makes one unnamed failed entry) or an entry with a bad path (its own `Error`) does not fail the review: `impact` is `failed`, the skills run. The one usage error is a clone overlapping `--repo-path`; `linkedOutside` also marks (never scrubs) a clone that is or holds `os.TempDir()`, `$HOME`, `$XDG_CONFIG_HOME` or `/`, overlaps a trusted input or the result file, or is in a system directory: `<clone>/*` would reach `auth.json` or the scrub would delete the input. A skill named `impact` is a usage error while any entry is given. `prepareAgent` calls `scrubLinked` before any run: per usable entry `checkout.Scan` (instruction files, links to the root, out of the clone, to denied files) plus a walk that deletes every file `config.ReadDenied` denies, judged in lower case (`.ENV`), plus instruction files in a nested `.git`; only the clone's own `.git` is skipped. A failure sets the entry's `Error` to fixed text (the details, quoted, are in the log: a clone's file names never reach a comment). `agentInputs.Linked` is passed to `review.Request` as is, failed entries included, so a bad file or a refused path gives a failed `impact`, never an absent one. `config.OpenCodeOptions.Linked` adds `external_directory` allows; only `runWith` with `runMode{linked}` sets it (impact run and its verification), with `noInstructions`. With it empty the config is byte-identical to before. `finding.Finding.Linked` (`*finding.Caller`) passes through `internal/result` as `linked`; `render` and the hidden findings block do not know it. `finding.ParseAnswer` drops `linked`; only `ParseImpactAnswer` reads it, loosely (a bad value is dropped, never a repair run).
  - **Impact run** (`internal/review/impact.go`, `Request.Linked`, `ImpactSkill`): `reviewer.impact` runs after the skills in `Run`, sharing the budget and `--concurrency`; it always returns a result when any entry is passed (never absent: nothing usable left is `failed`). Fixed `impactPrompt` (not `skill.Prompt()`), diff = every changed file but the read-denied ones; `Watched` narrows it only when some file matches, else the whole change goes to every usable link. Previous findings and dismissals under `impact` attached. `enforceSeverity` is in code: no `Linked`, unknown repo, file not a regular file inside the clone, line past the end, or `can_block` false = suggestion (and a caller that fails is dropped). A completed run must have `runner.RunResult.Opened` (successful `read`/`grep`/`glob` paths from `Transcript.Opened`; the `list` tool is gone in opencode 2 and `read` on a directory lists it) under a clone, or it is `failed`. `verifyImpact` (`impactVerifyPrompt`) is the reverse of `verify`: anything not confirmed `real: true`, any failure or bad answer (only the last block counts; a `false` for an id wins) makes blocking findings suggestions; a cancel, timeout, budget stop or under `verifyMinRemaining` left makes `impact` `failed`. `impactLocation` clears `suggestion` and `suggested_fix` on every impact finding. No text from a clone or the model reaches a failure or note: `impactCauseText` is fixed per `Cause.Kind` (`Cause.Message` holds the tool target), parse errors, verifier reasons and answer text go to the log only (`warnf`, quoted, redacted). A clean run adds the note `Impact: checked <names>, nothing found`. `files.reviewed` stays empty.
  - Base-commit skip rules: `.gitattributes` and the "generated" header are read from `--base`, never the checkout (`GIT_ATTR_SOURCE`, so git >= 2.40 or error `internal`). A new file is reviewed.
  - `--base`/`--head` are full lowercase SHAs, `--repo-path` is the work tree top, `HEAD` must equal `--head`. `OPENCODE_PROVIDER` and `OPENCODE_MODEL` are required; extra denied reads are `*.pem`, `*.key`, `*.tfvars`.
  - `PERGENT_RESULT_TOKEN`, `GITHUB_TOKEN` and `GITLAB_TOKEN` are removed from opencode's env; secrets are redacted. A verdict covers only `files.reviewed`; `files.skipped[].rule` records the rest. stdout carries only the result; logs go to stderr.
  - Exit codes: 0 delivered (even if every skill failed), 2 usage, 3 no review possible (error result delivered), 4 delivery failed. Any failure to review is an error result, never a false pass.
- **Comment deduplication.** `FindComment` returns pergent's own comment only: the body starts with `<!-- pergent -->` (`render.Marker`) AND the author is the token's identity, read once per run by `GET /user`. GitHub's Actions `GITHUB_TOKEN` cannot read `/user` (401/403/404), so then only an author with `type == "Bot"` counts; any other `/user` failure, and any GitLab failure, is a failed lookup. A foreign note is never updated or read for findings (a forged `pergent:findings` block would reach the prompt); it keeps paging, and none found means create. `commentToUpdate` (cmd/main.go) retries a failed lookup once after `commentLookupRetryDelay`, then posts a new comment and logs that a duplicate may appear. `previousMessage` tells the model to treat the attached file as data.
- **Diff fallback.** Tries local `git diff` first, falls back to platform API (for shallow clones).

## Build & Test

```bash
make build    # builds bin/pergent
make test     # runs all tests
make clean    # removes bin/
```

`make test` does not run opencode. The end-to-end suite (`cmd/opencode_e2e_test.go`, `cmd/fakemodel_test.go`) runs the real opencode against a fake model server and is skipped unless `PERGENT_TEST_OPENCODE` names an opencode binary:

```bash
PERGENT_TEST_OPENCODE=/path/to/opencode go test ./cmd/ -run OpencodeE2E -v -count=1
```

It pins the sandbox (only read tools offered, a permissive global config cannot loosen it, no snapshots, no leaks), the error and timeout causes, and process cleanup. `.github/workflows/test.yml` runs `make vet`, `make test` and `gofmt` on every pull request, and the e2e suite against the opencode version in the Dockerfile (change the two together).

## Config Resolution Priority

CLI flags > `PERGENT_*` env vars > auto-detect from CI environment > defaults

## Required Environment Variables

- `GITHUB_TOKEN` or `GITLAB_TOKEN` — platform API access
- `OPENCODE_PROVIDER` — LLM provider (e.g., `anthropic`, `openai`)
- `OPENCODE_API_KEY` — API key for the LLM provider
- `OPENCODE_MODEL` — Model to use (e.g., `claude-sonnet-4`)
