# pergent

CLI tool that runs agentic PR/MR reviews in CI/CD pipelines by spawning `opencode` as a subprocess.

## Architecture

- `cmd/main.go` — CLI entrypoint, flag parsing, orchestration
- `cmd/agent.go` — `pergent agent`: flags, checkout checks, scrub, run, delivery, exit codes
- `internal/skill/` — Parses `.md` skill files (YAML frontmatter `name`/`paths`/`exclude`/`cross_batch` + body); `Prompt()` adds the default `## Blocking` section and pergent's fixed output-format instructions. `LoadDir` takes `*.md` files and `<name>/SKILL.md` folders, symlinks followed (ConfigMap volumes); a folder without `SKILL.md` is an error
- `scope/` — Public package (`github.com/gopaytech/pergent/scope`, imports no pergent `internal/` package): the glob matcher (`Match`, `MatchAny`, and `CheckPattern`, which `internal/skill` runs on `paths`/`exclude` at load because `Match` reports a bad pattern as no match), the path-based default exclusions (`Attributes.PathRule`: lockfile, vendored, generated by `.gitattributes`, where the last matching line wins and `-linguist-generated`, `linguist-generated=false` or `!linguist-generated` un-marks), the generated-file header test, and `Decide`, which applies one skill's `paths`/`exclude` to a file. pergent.sh imports it, so the rule strings are a contract
- `internal/diff/` — Splits a unified diff into per-file patches, classifies default exclusions (deleted, binary, no content changes, then `scope`'s path rules and the patch's generated header), and groups files into token-budgeted batches
- `internal/finding/` — The `Finding` type (file, line, end_line, severity, title, explanation, fix, suggestion), stable fingerprints, dedup
- `internal/review/` — Runs a whole review: per skill selects files, batches them, runs one opencode run per batch (plus a repair run, an optional cross-batch run and a verification run), and decides each skill's verdict; one shared concurrency limit and time budget
- `internal/config/` — Resolves config (flags > env > auto-detect), generates temporary `opencode.json`
- `internal/runner/` — Spawns `opencode run` subprocess, parses NDJSON output, classifies the run (completed or failed with a cause), retries transient provider errors, enforces timeout and step limit (a stopped run kills opencode's whole process group, so its children die too; Unix only); passes opencode's stderr through redacted line by line
- `render/` — Public package (`github.com/gopaytech/pergent/render`, imports no pergent `internal/` package, redacts nothing): builds the review comment from `render.Skill` values. One header (headline with verdict and confidence, meta line, reason only when the score is below 5 or capped, skills table for several skills, failures), then the `**Summary:**` line (one skill, one batch, one summary), one findings list across skills (blocking open, suggestions collapsed), the Dismissed list, the details (a `- **Batch N of M:**` list for one skill with several batches; with several skills a `#### <skill>` section each holding its summary and checks; the checks by area, a heading and a `Check`/`Status`/`Detail` table per `Check.Section`, failed first, no-area checks last, under an `Other checks` heading beside named areas and with none alone, merged across batches per skill) and one `Files (N)` list, then the notes, the footer and the hidden findings block. Includes the shrink steps for a size limit (`shrinkSteps`, summaries cut last). `Options.Layout` (`blocks.go`: `Block`, `DefaultLayout`, `ParseLayout`; blocks `summary`, `findings`, `dismissed`, `checks`, `files`, each open or collapsed or left out; nil or invalid means the default; `findings` is required; it never changes a verdict, count or the fixed header and footer, and `Short` wins over it). Options: `Commit`, `FileURL` (`GitHubFileURL`/`GitLabFileURL` build one), `DismissCommand`, `Version`, `FindingsTitle`, `FindingNote`, `Inline` (fingerprints posted inline, left out of the lists), `Footer` (caller text before the hidden block), `MetaNote` (last part of the meta line), `Short` (leaves out the Files list and the passed and n/a checks, with no note; the size-limit steps still apply). Also `SkillScore`/`ReviewScore` (the confidence caps), `AssignIDs` (finding IDs) and `ApplyDismissals` (moves dismissed findings into a Dismissed section and recomputes verdicts). Model text goes through `lineText` (one line), `wrappedText` (between pergent's own `**`/`_`), `cellText` (table cell) or `blockText` (several lines) in `prose.go`. `lineText` leaves a line-start `#`, `>` or `-` alone, so a summary, an area name or a skill name is written only after a prefix of pergent's (`**Summary:** `, `- **Batch N of M:** `, `#### `). Fenced code is written again inside a fence pergent builds (no info string), a container of pergent's. A code span is the model's own bytes, kept only on a narrow rule (it starts at the line's start or after a space or tab, ends at the line's end or before a space, tab or `).,:;!?`, a line with a `$`, an odd number of backticks or any backtick outside a span keeps no span, and in `wrappedText` the line's start and end don't count; otherwise a URL or math could take a backtick); a cell keeps none. Every other `@`, `<`, `[`, `]`, `|`, stray backtick and entity start is broken with a zero-width joiner or a backslash, and `|` in a cell is `&#124;`. `testdata/golden` pins the comment byte for byte
- `internal/output/` — Converts per-skill review results to `render` types (redacting every text field first) and calls `render`; parses the hidden findings block back for `--previous-review`
- `internal/result/` — Agent-mode result: schema v1 types, error codes, finding IDs (`render.AssignIDs`), 10 MB size cap (`Encode`), delivery to file/stdout/HTTP (`Deliver`)
- `internal/checkout/` — Scans a checkout for instruction files and symlinks (to the root, outside it, or to a file a caller's rule denies); CI mode (`cmd/scrub.go`) and agent mode (`handleInstructionFiles`) decide what to delete or refuse
- `internal/redact/` — Removes credentials (token env values, bearer tokens, URL keys) from the comment and logs
- `internal/platform/` — GitHub/GitLab API clients for fetching diffs and posting/updating comments

## Key Concepts

- **One opencode run per batch.** Each `--skill` is reviewed over the changed files in its scope (`paths`/`exclude` plus default exclusions). `internal/diff` groups those files into batches that fit a quarter of the model's context, and `internal/review` runs one `opencode run` per batch, all skills and batches in parallel. Results are combined into one comment.
- **Structured findings.** The prompt (`skill.Prompt()`) tells the model to end with one `json` block of findings; severity is `blocking` or `suggestion`. The answer also carries `confidence` 1–5 with `confidence_reason`, and a finding may carry `end_line` and `suggestion` (exact replacement text, at most 10 lines); bad values are dropped, never a repair run. The answer is the last block with a `findings` key; a bad or unreadable last block is malformed, never replaced by an earlier block (that may be an example of the shape). A malformed answer gets one repair run, then the batch is a failure. Skills must not carry their own output-format instructions.
- **Change description.** `review.Request.Description` is the change's title and description (CI mode: `Platform.FetchChangeDescription`, a failure is a warning; agent mode: `--change-description`, default `$PERGENT_CHANGE_DESCRIPTION`, same trust and warn-and-ignore rules as `--previous`). `changeText` removes HTML comments (one left open hides the rest), trims it and cuts it to 16 KiB. `reviewBatch` and `crossBatch` attach it as `change-description.md` with `changeMessage`; verification and repair runs never get it, so the author's text can't talk a blocking finding away. `changeMessage` is the design: intent can excuse a change in behaviour but never a blocking problem, a contradiction is always a `suggestion` (verification couldn't confirm a blocking one), a promise the run doesn't see is not reported (a run sees part of the change), and the description itself is never a finding. The file is data; the wording is all that stops it swaying the review run.
- **On-demand diffs.** `review.Run` (only with a generated config, i.e. `OPENCODE_PROVIDER` set) writes each eligible file's patch (some skill reviews it, no default exclusion, patch fits a batch, neither its path nor a rename's old path denied by `config.ReadDenied`) to `NNNN.patch` plus one `index.txt` (diff file, size, `strconv.Quote`d path) in one `pergent-diffs-*` temp directory, removed when the review ends or a run's own goroutine panics. Nothing is attached and `changed-files.md` is unchanged; batch, cross-batch and verification runs get one message sentence naming the index, unless their own diff covers every indexed file. A directory or file that cannot be written is a warning, never a failure. Findings are not filtered by file; the scope is prompt wording only. A run can read the diffs; nothing proves it does.
- **Deleted files.** They stay skipped (rule `deleted`, confidence cap 4, Files list and result schema unchanged). With `--check-deleted` (default true; `PERGENT_CHECK_DELETED`, flags > env, a bad value is a config error; `Request.CheckDeleted`) `reviewer.deletedPaths` gives each skill the deleted files in its scope: `scope.Decide` on its `paths`/`exclude`, with the path rules (`Classifier.PathRule`: lockfile, vendored, `.gitattributes` generated) a deleted file would meet if it still existed. They go to the skill's batch, cross-batch and verification runs (not repair) as `deleted-files.md` (`strconv.Quote`d, 200 paths then `... and N more`) with `deletedMessage` / `verifyDeletedMessage`; the message says the findings may be on files outside the diff. A skill with a deleted list but no batch gets one `reviewBatch` call on zero files (no `diff.patch`, `noDiffMessage`, label `deleted`), folded in by `takeDeletedOnly`: only its findings count (no `Batches`, `Reviewed`, summary, checks or confidence), and a failed run is a note, never a `failed` verdict, so a delete-only change keeps today's verdict. Off changes nothing, byte for byte.
- **Verdicts.** Each skill is `no_blocking_issues`, `has_blocking_issues` or `failed` (any batch failure). Blocking findings are re-checked by a separate verification run before they count; `cross_batch: true` adds one run for problems spanning batches.
- **One budget, one concurrency limit.** `--timeout` bounds the whole review (not each run) and `--concurrency` caps opencode runs in flight across all skills and batches.
- **Previous review.** `--previous-review` reads the hidden `<!-- pergent:findings ... -->` block (last line of the comment) and attaches each skill's findings, only when non-empty. Comments from older versions have no block and count as a first review; a corrupt block logs a warning and is ignored. A fingerprint the model reuses is kept only on the same file and line as the previous finding: a dismissal is keyed by fingerprint, so a new finding elsewhere must not inherit one.
- **Read-only agent.** The generated `opencode.json` defines a `pergent` agent (set as `default_agent` and passed via `--agent`) and denies edit/bash/task/skill/webfetch/websearch and `*.env` reads — the agent can only read files, grep, glob, and list. `OPENCODE_DISABLE_PROJECT_CONFIG=true` stops the reviewed repo's own opencode config from overriding this. It also sets `lsp: false`: the `read` tool starts language servers past the permissions, and one can be a program from the reviewed repo (`node_modules/.bin/biome`). opencode 1.19 leaves them off when unset, older versions don't.
- **Symlinks.** opencode's path checks are lexical: `read` checks the link's own path, then reads through it. `internal/checkout` holds the shared scan (instruction files, links to the root, links that leave the checkout). CI mode's root `AGENTS.md`/`CLAUDE.md` (`config.projectInstructions`) is used only if its real path is a regular file inside the checkout (root resolved too) that `config.ReadDenied` allows (same deny flag as the run); otherwise it is skipped with a warning and the next name is tried. Platform CI mode (`scrubCheckout` in `cmd/scrub.go`, called in `main` just before `review.Run`) deletes every symlink whose target resolves outside the checkout, or whose real target `config.ReadDenied(rel, false)` denies (the read rules match the name that is read, not where a link leads), and logs it; a failure to delete or read is a warning, never a stop. A dangling link is judged by where its text leads through the symlinks that exist (`looseTarget`), so one that cannot be shown to stay inside counts as leaving. `--local` never deletes: it is the user's own working tree and trusts the checkout.
- **Own-config mode.** With `OPENCODE_PROVIDER` empty pergent writes no config: no sandbox, project config on, default agent, and `GITHUB_TOKEN`/`GITLAB_TOKEN` stay in opencode's env (it may sign in with one; the runner removes them only with a generated config). `config.Resolve` therefore refuses it in platform mode (an unset CI variable expands to ""), unless `PERGENT_USE_OPENCODE_CONFIG=true` (a bad value is a config error); then it warns. `OPENCODE_MODEL` without a provider is part of that error, a warning with `--local`. `--local` needs no opt-in; agent mode always requires a provider. The prompt lives only in the config, so `runWithPrompt` (the one place every prompt passes: batch, repair, cross-batch, verification) attaches it as `review-instructions.md`, first among the run's files, adds `promptMessage` to the message, and removes it with the run.
- **Config isolation.** `opencode.json` is written to a temp directory and passed via `OPENCODE_CONFIG` env var. The agent prompt is not in it: opencode expands `{env:}`/`{file:}` over the whole config text, so a skill body naming `{env:GITLAB_TOKEN}` would leak it and a stray `{file:x}` would fail every run. The prompt goes to `agent-prompt.md` (0600) beside it and the config holds `{file:<abs path>}`; a file's content is not scanned again. Each run (and each retry) also gets its own temp `XDG_DATA_HOME` (with the user's `auth.json` copied in): parallel runs sharing a fresh data dir race on opencode's SQLite migration and the losers exit 1. Its name (`config.DataDirPrefix`) must not start with `pergent-`, or the `pergent-*` read allow would cover `auth.json`; only its `opencode/tool-output` folder is allowed, since opencode points the model at long tool results there. With a generated config `GITHUB_TOKEN` and `GITLAB_TOKEN` are removed from opencode's env in every mode.
- **Run outcome.** Every opencode run is `StatusCompleted` (the model's own final answer) or `StatusFailed` with a `Cause` (context overflow, timeout, opencode error event, step limit, non-zero exit, no answer, or cancelled when the caller's context ended, e.g. SIGTERM). A line over 16 MB stops the parse (`Transcript.ReadErr`): the run is `no_answer` with its own message, never a pass on an earlier answer. Only assistant text from a step that ended on its own counts as the answer; `synthetic` text and text outside `step_start`/`step_finish` never do. A failed batch makes its skill's verdict `failed` and is reported in the comment and log, but keeps the CI job green; only config errors before any review exit non-zero.
- **No auto-compaction.** The generated config sets `compaction.auto: false` and leaves model limits to opencode's registry (`--context-limit` overrides; `--max-tokens` is deprecated and ignored). The model is always declared under `provider.<id>.models`, or opencode can't find models behind a custom base URL.
- **Retries.** A run that fails on a transient provider error (429, 5xx, connection) is started again up to 3 times with backoff, within the review budget. opencode retries 5 times internally first.
- **Agent mode.** `pergent agent` reviews `--base..--head` in a checkout the caller prepared and delivers a versioned JSON result (`docs/agent-result-schema.md`). It holds no platform token and never calls GitHub/GitLab; CI mode is untouched. Details:
  - Trusted inputs only: instructions, skills, `--previous`, `--carried`, `--dismissals` and `--change-description` come from paths passed in (the description's text is still the author's); one that resolves inside `--repo-path` is a usage error, as are a `--result` file, `$HOME` or `$XDG_CONFIG_HOME` there, and duplicate skill names. The checkout's `AGENTS.md`/`CLAUDE.md`/`CONTEXT.md` are never loaded.
  - `--scrub-instructions` deletes those files (root included), symlinks resolving outside the checkout and symlinks whose real target `config.ReadDenied(rel, true)` denies (`safe.txt -> prod.env`); without it, nested files or such symlinks give `untrusted_instructions`. A directory the scan cannot read is `internal`. opencode loads nested instruction files on every read whatever the project-config switch says.
  - `--carried` is a JSON file `{"<skill>": ["path", ...]}` of files a previous review covers: `reviewSkill` leaves them out of the batches (still in `changed-files.md`), drops previous findings on them, and reports them as `files.carried`. Same trust and warn-and-ignore rules as `--previous`.
  - `--dismissals` (default `$PERGENT_DISMISSALS`) is a JSON file `{"<skill>": [{file, title, severity, reason}, ...]}` of findings people rejected: `reviewBatch` and `crossBatch` attach a skill's list as `rejected-findings.json` with `rejectedMessage`, `verify` gets only the `blocking` entries with `rejectedVerifyMessage`, the repair run none. Data, never instructions; same warn-and-ignore rules as `--previous`. Logged as `dismissals: <skill>=<n>`, not part of the result.
  - `--linked-repos` (default `$PERGENT_LINKED_REPOS`; a flag with an env default, as `--change-description`) is a JSON file `[{name, path, watched, can_block, error}]` (`review.LinkedRepo`, `cmd/linked.go`), at most 3. A file that can't be used (unreadable, malformed, more than 3, a duplicate or empty name: `failedLinks` makes one unnamed failed entry) or an entry with a bad path (its own `Error`) does not fail the review: `impact` is `failed`, the skills run. The one usage error is a clone overlapping `--repo-path`; `linkedOutside` also marks (never scrubs) a clone that is or holds `os.TempDir()`, `$HOME`, `$XDG_CONFIG_HOME` or `/`, overlaps a trusted input or the result file, or is in a system directory: `<clone>/*` would reach `auth.json` or the scrub would delete the input. A skill named `impact` is a usage error while any entry is given. `prepareAgent` calls `scrubLinked` before any run: per usable entry `checkout.Scan` (instruction files, links to the root, out of the clone, to denied files) plus a walk that deletes every file `config.ReadDenied` denies, judged in lower case (`.ENV`), plus instruction files in a nested `.git`; only the clone's own `.git` is skipped. A failure sets the entry's `Error` to fixed text (the details, quoted, are in the log: a clone's file names never reach a comment). `agentInputs.Linked` is passed to `review.Request` as is, failed entries included, so a bad file or a refused path gives a failed `impact`, never an absent one. `config.OpenCodeOptions.Linked` adds `external_directory` allows; only `runWith` with `runMode{linked}` sets it (impact run and its verification), with `noInstructions`. With it empty the config is byte-identical to before. `finding.Finding.Linked` (`*finding.Caller`) passes through `internal/result` as `linked`; `render` and the hidden findings block do not know it. `finding.ParseAnswer` drops `linked`; only `ParseImpactAnswer` reads it, loosely (a bad value is dropped, never a repair run).
  - **Impact run** (`internal/review/impact.go`, `Request.Linked`, `ImpactSkill`): `reviewer.impact` runs after the skills in `Run`, sharing the budget and `--concurrency`; it always returns a result when any entry is passed (never absent: nothing usable left is `failed`). Fixed `impactPrompt` (not `skill.Prompt()`), diff = every changed file but the read-denied ones; `Watched` narrows it only when some file matches, else the whole change goes to every usable link. Previous findings and dismissals under `impact` attached. `enforceSeverity` is in code: no `Linked`, unknown repo, file not a regular file inside the clone, line past the end, or `can_block` false = suggestion (and a caller that fails is dropped). A completed run must have `runner.RunResult.Opened` (successful `read`/`grep`/`glob`/`list` paths from `Transcript.Opened`) under a clone, or it is `failed`. `verifyImpact` (`impactVerifyPrompt`) is the reverse of `verify`: anything not confirmed `real: true`, any failure or bad answer (only the last block counts; a `false` for an id wins) makes blocking findings suggestions; a cancel, timeout, budget stop or under `verifyMinRemaining` left makes `impact` `failed`. `impactLocation` clears `suggestion` and `suggested_fix` on every impact finding. No text from a clone or the model reaches a failure or note: `impactCauseText` is fixed per `Cause.Kind` (`Cause.Message` holds the tool target), parse errors, verifier reasons and answer text go to the log only (`warnf`, quoted, redacted). A clean run adds the note `Impact: checked <names>, nothing found`. `files.reviewed` stays empty.
  - Base-commit skip rules: `.gitattributes` and the "generated" header are read from `--base`, never the checkout (`GIT_ATTR_SOURCE`, so git >= 2.40 or error `internal`). A new file is reviewed.
  - `--base`/`--head` are full lowercase SHAs, `--repo-path` is the work tree top, `HEAD` must equal `--head`. `OPENCODE_PROVIDER` and `OPENCODE_MODEL` are required; extra denied reads are `*.pem`, `*.key`, `*.tfvars`.
  - `PERGENT_RESULT_TOKEN`, `GITHUB_TOKEN` and `GITLAB_TOKEN` are removed from opencode's env; secrets are redacted. A verdict covers only `files.reviewed`; `files.skipped[].rule` records the rest. stdout carries only the result; logs go to stderr.
  - Exit codes: 0 delivered (even if every skill failed), 2 usage, 3 no review possible (error result delivered), 4 delivery failed. Any failure to review is an error result, never a false pass.
- **Comment deduplication.** `FindComment` returns pergent's own comment only: the body starts with `<!-- pergent -->` (`render.Marker`) AND the author is the token's identity, read once per run by `GET /user`. GitHub's Actions `GITHUB_TOKEN` cannot read `/user` (401/403/404), so then only an author with `type == "Bot"` counts; any other `/user` failure, and any GitLab failure, is a failed lookup. A foreign note is never updated or read for findings (a forged `pergent:findings` block would reach the prompt); it keeps paging, and none found means create. `commentToUpdate` (cmd/main.go) retries a failed lookup once after `commentLookupRetryDelay`, then posts a new comment and logs that a duplicate may appear. `previousMessage` tells the model to treat the attached file as data.
- **Diff fallback.** Tries local `git diff` first, falls back to platform API (for shallow clones).

## Build & Test

```bash
make build    # builds bin/pergent
make test     # runs all tests
make clean    # removes bin/
```

## Config Resolution Priority

CLI flags > `PERGENT_*` env vars > auto-detect from CI environment > defaults

## Required Environment Variables

- `GITHUB_TOKEN` or `GITLAB_TOKEN` — platform API access
- `OPENCODE_PROVIDER` — LLM provider (e.g., `anthropic`, `openai`)
- `OPENCODE_API_KEY` — API key for the LLM provider
- `OPENCODE_MODEL` — Model to use (e.g., `claude-sonnet-4`)
