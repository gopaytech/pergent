# Agent sandbox

When `OPENCODE_PROVIDER` is set, pergent writes a temporary `opencode.json` for each opencode run and points opencode at it with `OPENCODE_CONFIG`. That config:

- defines a `pergent` agent that carries the skill's prompt (its body plus pergent's output-format instructions) and `--max-turns` as its step limit, and makes it the default agent (pergent also passes `--agent pergent`). The prompt is written to a file next to `opencode.json` (mode 0600, removed with it) and the config names the file with `{file:...}`, because opencode expands `{env:VAR}` and `{file:path}` anywhere in a config's text: a skill that mentions `{env:GITLAB_TOKEN}` or `{file:missing}` reaches the model exactly as written
- is an allow-list: every tool is denied (`"*": "deny"`), then only `read`, `glob` and `grep` are allowed, so edits, shell commands, subagents, skills and web access stay denied, and so does any tool a later opencode version adds. The same permissions are set on the `pergent` agent itself, so a global opencode config on the machine cannot loosen them. A few paths outside the checkout are allowed for reading: pergent's own temporary files (the diffs, the attached files) and the folder where opencode saves long tool results
- denies reading `*.env` / `*.env.*` files (except `*.env.example`). opencode's `grep` and `glob` don't apply these read rules (and `grep` searches hidden files), so in platform mode and agent mode pergent also deletes such files from the checkout before any run; see below
- sets `lsp: false`. opencode 2 never starts language servers, but the setting is kept: a server can be a program from the reviewed branch (such as `node_modules/.bin/biome`), and an older opencode or a global config could turn it on
- turns off opencode's snapshots (`snapshot: false`), which would run git in the checkout and write to its object store
- turns off opencode's auto-compaction (`compaction.auto: false`), so a run that fills the model's context fails with the overflow error instead of continuing from a summary
- leaves the model's context and output limits to opencode's model registry, unless you set `--context-limit`

Every `opencode run` starts with `--standalone`, so it uses its own server and reads this config: a plain run could attach to a shared server that ignores it. Each run also gets its own empty state directory (`XDG_STATE_HOME`), and `PWD` is set to the checkout, because opencode 2 takes its project directory from `$PWD`.

pergent also sets `OPENCODE_DISABLE_PROJECT_CONFIG=true` and its newer name `OPENCODE_CONFIG_PROJECT_DISABLE=true`, replacing any value you set, so an `opencode.json` or `.opencode/` directory (agents, plugins, commands) in the reviewed branch can't change these permissions or run plugin code while your LLM key is in the environment. Because `OPENCODE_DISABLE_PROJECT_CONFIG` also stops opencode from finding `AGENTS.md` / `CLAUDE.md` by itself, pergent passes the root file to opencode explicitly. `OPENCODE_DISABLE_CLAUDE_CODE=true` stops opencode 2 from also reading `CLAUDE.md` files from your home directory, and `OPENCODE_DISABLE_AUTOUPDATE=true` means a run makes no update check and the binary can't change during a review.

opencode does not inherit pergent's whole environment. A CI job's environment can hold deploy tokens and cloud credentials, and a change under review could try to reach them, so only an allow-list passes:

- process basics: `PATH`, `HOME`, `USER`, `USERNAME`, `LOGNAME`, `SHELL`, `TMPDIR`, `TMP`, `TEMP`, `LANG`, `TZ`, `TERM`, and every `LC_*`;
- proxies: `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `ALL_PROXY` and their lower-case names;
- certificates: `SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS`, `NODE_USE_SYSTEM_CA`, `NODE_USE_ENV_PROXY`, `NODE_TLS_REJECT_UNAUTHORIZED`;
- `XDG_CONFIG_HOME`, `XDG_CACHE_HOME` and `OPENCODE_API_KEY`;
- cloud providers, so a provider that signs in with your cloud credentials still works: every variable starting `AWS_`, `GOOGLE_`, `VERTEX_`, `AZURE_` or `CLOUDFLARE_`.

Everything else is dropped, including `GITHUB_TOKEN`, `GITLAB_TOKEN` and every other `OPENCODE_*` variable you set, such as `OPENCODE_CONFIG_CONTENT` (it is merged over pergent's config and could loosen the permissions), `OPENCODE_CONFIG_DIR` (opencode loads it as a config directory with plugins, so one inside the checkout would run the branch's code with your key in the environment), `OPENCODE_FLAGS`, `OPENCODE_DB`, `OPENCODE_TEST_HOME` and `OPENCODE_SIMULATE` (unvetted features, one database shared between runs, test hooks). pergent then sets `OPENCODE_CONFIG`, the two project-config switches, `OPENCODE_DISABLE_CLAUDE_CODE`, `OPENCODE_DISABLE_AUTOUPDATE` and `PWD`.

To pass another variable, list its name in `PERGENT_OPENCODE_ENV`, comma-separated and exact (`PERGENT_OPENCODE_ENV=OTEL_EXPORTER_OTLP_ENDPOINT,MY_CA_BUNDLE`). A name that is not a plain variable name, starts with `OPENCODE_` or `PERGENT_`, or is `GITHUB_TOKEN`, `GITLAB_TOKEN`, `PWD`, `XDG_DATA_HOME` or `XDG_STATE_HOME` is a config error (`usage` in agent mode), so the list cannot reopen what pergent removes or sets. `OTEL_*` is not passed unless you list it: opencode 2 exports traces when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, and traces can include prompt and repository text. When pergent uses your own opencode config, none of this applies: opencode gets pergent's whole environment.

opencode checks the path it is asked to read, not where a symlink leads, so a link in the reviewed branch could expose a file beyond the checkout (`x -> /etc/passwd`, `x -> ..`). In platform mode (GitHub or GitLab CI), before any run, pergent deletes every symlink in the checkout whose target resolves outside it, or whose real target the read rules deny (`safe.txt -> prod.env`; the rules match the name being read, not where a link leads), and logs each path. `.git` is skipped. A link that dangles counts as leaving unless its target can be shown to stay inside. The link is deleted, never its target, and the review goes on; a link that cannot be deleted, or a directory that cannot be read, is a warning. `--local` never deletes anything: it reviews your own working tree and trusts the checkout. (Agent mode: see `--scrub-instructions`.)

In platform mode, before any run, pergent also deletes every file in the checkout that the read rules deny (`config/prod.env`, `.env.local`), tracked or not, and logs each path. A name is judged as written and in lower case, so `PROD.ENV` goes too. Only the checkout's own `.git` is skipped. The review's diff compares commits, so a change to such a file is still reviewed; only the copy on disk goes, so that `grep` can't search it. A file that cannot be deleted is a warning and the review goes on. Agent mode does the same with its wider rules, and stops with `internal` when a file can't be deleted or a directory can't be read. `--local` deletes nothing, so there a denied file in your working tree can still be found with `grep`.

Each opencode run also gets its own empty `XDG_DATA_HOME`, removed when the run ends. The agent can read only the `tool-output` folder in it, where opencode saves a long tool result, not the rest (your `auth.json` and the session database). opencode creates its SQLite database there on first start, and runs started at the same moment in one fresh directory (a new CI container) race on that setup. The losers exit before the model's first step. Your `auth.json`, if you have one, is copied in, and opencode 2 imports it on start, so a login made with opencode 1.x still works. A login made with opencode 2 (`opencode auth login`) is kept in opencode's database, which pergent does not copy, so it does not reach a run. Give the key through `OPENCODE_API_KEY` when pergent generates the config, or through the provider's environment variable or your opencode config when it uses yours.
